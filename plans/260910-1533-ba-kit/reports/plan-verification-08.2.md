## Load-bearing REFUTED

**Claim #28 — Gate 4's causal attribution is false; the invariant it's meant to guard is unenforced on real installs.**

Ran the gate's own script verbatim: fresh temp dir → `git init` → `node bin/ck.js init --kit ba` → touch a file under `plans/ba/demo/deliverables/` → `git check-ignore`. Result: `TRACKED` (boolean outcome matches the phase's expectation). But the *reason* the phase gives — "via `.gitignore:72`'s `!plans/**/deliverables/*.md`" — is false for what the script actually exercises:

- `.gitignore:72` is a line in **ClauKit's own repo root `.gitignore`**. It is never copied to an install — `bin/lib/gitignore-wire.js` (the only code that writes a project's root `.gitignore` on `ck init`) works from a hardcoded `PLAN_RULES` array (L58-62): `plans/**/reports/review-package-*.md`, `plans/**/reports/*-brief-*.md`, `plans/**/*.derived.json`. No `plans/**/*` broad ignore, no `!plans/**/deliverables/*.md`.
- Verified directly: `cat "$P/.gitignore"` in the fresh install shows only the header comment + those 3 `PLAN_RULES` lines — no deliverables rule, no broad `plans/**/*` ignore at all.
- So `TRACKED` in the fresh install happens because the installed `.gitignore` never ignores `plans/**` in the first place — an accident of the test fixture (a brand-new empty repo) — not because the specific allowlist rule propagated.

Why load-bearing: Gate 4's exit criterion is `TRACKED`, and the phase treats this as proof the "committed billing document" invariant (D-11, extended to `owned`/`derived` deliverables) holds for real consumers. It does not: if a consumer project's *own* pre-existing `.gitignore` already has a broad `plans/**`-style ignore (plausible — this is exactly the pattern ClauKit's own repo uses), `ck init` would never add a deliverables-unignore rule, because `PLAN_RULES` doesn't carry one, and `wireOne()` only appends rules already in that list. The billing document would be silently gitignored, contradicting the phase's central premise.

Phase 08.1 explicitly hit this same fork for the entities allowlist (`!plans/**/entities/*.md`) and stated a reason for **not** touching `PLAN_RULES` (task 8.1.9). Phase 08.2 makes no equivalent mention of `gitignore-wire.js`/`PLAN_RULES` anywhere in its text (`grep -n "gitignore-wire\|PLAN_RULES" phase-08.2-ba-deliver.md` → no hits) — the question was never asked for `deliverables/`. Gate 4 as scripted cannot catch this because its fixture (a brand-new temp repo) can never have a pre-existing conflicting `.gitignore`.

Settling check for whoever picks this up: add a `PLAN_RULES` entry `!plans/**/deliverables/*.md` (mirroring the root `.gitignore`'s line 72), or make Gate 4's fresh-install fixture start from a `.gitignore` that already ignores `plans/**` broadly (closer to a real consumer) before asserting `TRACKED`.
