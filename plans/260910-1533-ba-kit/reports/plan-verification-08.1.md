## Load-bearing REFUTED

1. **Task 8.1.6 fixture spec + Gate 1 (#22, #23) — the demo tree does not have `FR-002`/`FR-003`.** As of this check the only FR entities in `plans/ba/demo/entities/` are `FR-011.md` and `FR-012.md` (confirmed twice, and the file set changed under me between checks — another agent is actively renumbering `plans/ba/demo/**`). Task 8.1.6 hard-codes `CR-001 parents:[FR-002]` / `CR-002 parents:[FR-003]`, and Gate 1's expected `changelog --json` output hard-codes `parents=FR-002,FR-003`. If the demo tree settles with `FR-011`/`FR-012` (or anything else), both task 8.1.6 and Gate 1 as literally written will not match reality — the implementer must read the actual FR ids off the tree at execution time, the same way Gate 4 already self-flags for its `AC-*` id ("Substitute any `AC-*` id the demo tree actually holds") but Gate 1/task 8.1.6 do not carry that same caveat for FR ids. Every gate/task built on top (Gate 1, Gate 3's `sed` edits naming `FR-002.md`) inherits this.

2. **Gate 8's `git check-ignore` exit-code assumption is backwards for negated (allowlisted) patterns.** Gate 8 expects `entity-ignored=1`, `cr-ignored=1`, `deliverable-ignored=1` (interpreted as "not ignored" post-fix). Empirically, on the live repo `git check-ignore -v plans/ba/demo/deliverables/SRS-001.md` → prints the matching `!plans/**/deliverables/*.md` rule and **exits 0**, even though the file is genuinely not ignored (confirmed independently via `git status --porcelain --ignored=matching` → `??`, and `git add -n` → would add it). Reproduced in an isolated scratch repo with the identical 3-line `.gitignore` skeleton (`plans/**/*` / `!plans/**/` / `!plans/**/deliverables/*.md`), and again after adding the exact line task 8.1.9 proposes (`!plans/**/entities/*.md`) against a scratch entities file — same result: exit **0**, not 1. Root cause: `git check-ignore`'s exit status reflects "some pattern matched this path" (positive or negative), not "the path is excluded" — it only differs from that for a *simple* top-level negation with no directory-unignore chain (e.g. `.env*` + `!.env.example` correctly gives exit 1, no output) but not for the nested `!dir/` + `!dir/*.ext` idiom this repo uses for `plans/**/`. **As written, Gate 8 will read `entity-ignored=0`, `cr-ignored=0`, `deliverable-ignored=0` — the opposite of its stated expectation — even when task 8.1.9's fix is implemented correctly.** The gate needs a different check (e.g. `git status --porcelain --ignored=matching` producing `??` not `!!`, or `git check-ignore -v` output text-matched for a leading `!` in the pattern column) rather than a bare exit-code compare.
