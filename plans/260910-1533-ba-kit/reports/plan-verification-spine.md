## Consistency findings

**(a) Do phase 02's frontmatter keys / `KIND_ORDER` / regexes match plan.md § Spine model verbatim?**

Mostly yes (task 2.2 explicitly instructs "copy verbatim from plan.md"), with one count mismatch: plan.md:163 headlines the table **"Ten frontmatter keys — eight required, two conditional"** (10 rows: `id kind project title doc parents source confidence out_of_scope touches`). Phase 02 refers to it twice as **"the 8 frontmatter keys"** (`phase-02-traceability-spine.md:45`) and **"the 8-key frontmatter table"** (`:54`) — undercounting by the two conditional keys (`out_of_scope`, `touches`) that phase 02's *own* parser (task 2.4) explicitly validates (`missing-out-of-scope`, `out-of-scope-on-wrong-kind`, `bad-touches`). Plan.md itself uses the same "8-key contract" shorthand once (`plan.md:178`, referring to the pre-D-10-addendum base), so the phrase has a legitimate reading, but task 2.2's instruction to "copy verbatim... the 8-key frontmatter table" risks an implementer copying only 8 of the 10 rows into `references/id-scheme.md`, since no table in plan.md is actually titled or sized "8-key". Not found: any restated regex text in phase 02 that diverges from plan.md's `DOC_ID`/`ITEM_ID`/`KIND_ORDER` — phase 02 defers to task 2.2's copy-verbatim instruction rather than re-deriving them, so no textual drift there.

**(d) Does any phase gate reference a command that does not yet exist and is not created by an earlier phase?**

Yes — **phase 02's own Gate 6 is the case**, and the plan's own text elsewhere says this exact thing will fail:

- Phase 02 Gate 6 runs `node <repo>/bin/ck.js init --kit ba` inside a fresh scratch git repo, then checks that `wireGitignore` correctly ignored `traceability.derived.json` while tracking `entities/FR-001.md`, `deliverables/SRS-001.md`, `plans/x/reports/code-review.md`.
- `ba.json`'s manifest (phase 01 task 1.1) declares `"workflows": [".claude/workflows/business-analysis-rules.md"]` as a required path — a file that **phase 03**, not phase 02, creates (`phase-03-rules-readme-capability-map.md`: "Produces: `.claude/workflows/business-analysis-rules.md` §§ 1–8").
- **Phase 01 itself already states this will fail**: task 1.2 — *"A manifest path that does not exist aborts `ck init` for every user (`bin/ck.js:49`, `checkKitPathsAvailable`), so the manifest cannot ship before phases 02–08 fill these — see the gate ordering below."* Plan.md's own § "Ordering constraint" reinforces it: *"`ck init --kit ba` cannot be run until 02–08 have filled the declared trees... Phase 01's Gate 1 ... runs immediately; its Gates 2–3 (a clean install) run last."*
- Verified in code: `bin/ck.js:49-54` calls `checkKitPathsAvailable(kit)` (= `fs.existsSync` over every declared path, `bin/lib/kit-resolver.js:123-125`) and `process.exit(1)` on any miss, **before** `wireGitignore(projectRoot)` at `bin/ck.js:158` ever runs.
- Phase 02 and phase 03 are **siblings**, not sequential (plan.md's phase table: `02 | ... | 01` and `03 | ... | 01`; the ASCII dependency graph shows `01 ──┬─> 02` and `01 ──> 03` as parallel branches). Nothing in the plan guarantees phase 03 has already produced `business-analysis-rules.md` by the time phase 02's own Gate 6 is executed (and per the plan's own file-numbering / linear task order, 03 runs *after* 02).
- Gate 6's script swallows the exit code (`>/dev/null 2>&1`, unchecked) and proceeds regardless, so a `ck init` failure at line 49 would silently skip `wireGitignore`, leaving the scratch repo's `.gitignore` unwired — which would make the gate's own `IGNORED …traceability.derived.json` assertion **fail**, not merely produce a misleading pass.

This directly contradicts plan.md's explicit policy (quoted above) that a real "clean install" run is deferred to phase 01's Gates 2–3, run **last** — phase 02 embeds one anyway, mid-sequence, using a manifest that (by phase 01's own admission) is not yet installable.

Phase 04 (`phase-04-ba-plan-and-context-hub.md`, the phase that actually specifies `/ba:plan`'s behavior in detail) contains **no** mention of any gitignore-related print line at all — it does not corroborate phase 06's claim. Given D-12 explicitly made `ck init --kit ba` a real, working one-step install (plan.md § D-12, § D-10 table: "Install: `ck init --kit ba`"), phase 02's framing (installer handles it) is the one consistent with the rest of the plan; phase 06 task 6.5's line appears to be an un-updated leftover from a pre-D-12 draft.
